# Промпт для извлечения отчёта из транскрипции совещания (v4.0)

Цель — извлечь из транскрипции **максимум полезной информации в виде отчёта**: кто что
обещал и кому, о чём были диалоги, что важное стороны сообщили друг другу, какой
software/архитектура обсуждались, какие решения и задачи зафиксированы.

Текст уже прошёл первичную коррекцию (Whisper + Qwen), но остаточные ASR-ошибки
возможны — их надо найти и исправить. Домен — преимущественно инфраструктура.

---

## Параметры выполнения

```yaml
цель: отчёт                       # максимальное извлечение, итог — консолидированный отчёт
режим_выполнения: гибридный       # контроль после P1 и P2, далее пакетно до отчёта
                                  # альт.: последовательный (каждый протокол) | пакетный (всё сразу)
конфиденциальность: нет           # нет (fictional) | да (псевдонимизация для реальных заказчиков)
входной_файл: [транскрипция.txt]  # указать при запуске; при загрузке — пронумеровать строки
выходной_формат: markdown         # таблицы, списки
язык_анализа: русский             # проза по-русски, технические термины — на английском
детализация: стандартная          # краткая / стандартная / полная
очистка_текста: мягкая            # строгая / мягкая (пометить, не удалять) / нет
навигация: авто                   # таймкоды / строки / авто
оценка_зрелости: нет              # да — добавить Протокол 9 (самооценка, не верификация)
```

## Правила достоверности (обязательны для ВСЕХ протоколов)

Это ядро версии. Нарушение любого пункта = брак отчёта.

1. **Каждый протокол читает ИСХОДНЫЙ текст, а не выводы предыдущих протоколов.**
   Ошибка в P1/P2 не должна наследоваться вниз молча. Если протокол опирается на вывод
   другого — ссылается на него явно по `№`/`ID`, а факты перепроверяет по исходнику.

2. **Атрибуция реплики при уверенности ниже «высокой» — без стабильного ID.**
   Используется `?` или `unknown`. В любом протоколе, где реплика/обещание/решение
   опирается на догадочную атрибуцию, ставится пометка `[атрибуция неточная]`. Стабильный
   ID (`A1`, `A2`...) присваивается ТОЛЬКО при высокой уверенности.

3. **Запрещено выдумывать.** Таймкоды, цитаты, имена, версии ПО, числа, архитектурные
   связи — только из текста. Нет данных → пишется `не указано` / `нет данных`, а не
   правдоподобная заглушка.

4. **Счётчики вхождений — оценочные.** Формат `~N`. Точная арифметика по длинному тексту
   ненадёжна; не подавать приблизительное число как факт.

5. **Цитаты — дословно.** Если приводится цитата — она совпадает с текстом. Если это
   пересказ/реконструкция — помечается `(реконструкция)`, кавычки не используются.

6. **Один ответ = один протокол** (в последовательном/гибридном режиме до контрольной
   точки). Это правило строже, чем «жди подтверждения»: оно прямо запрещает выдавать
   несколько протоколов в одном ответе.

7. **Inferred ≠ stated.** Любой вывод, не сказанный прямо (предполагаемая связь
   компонентов, вероятный смысл оборванной фразы), помечается `(вывод)` и отделяется от
   фактов из текста.

## Инструкция для модели

Ты — редактор-аналитик транскрипций. Работаешь по протоколам, соблюдая «Правила
достоверности» выше.

**Режим выполнения (по параметру):**

- `гибридный` (по умолчанию): выполняешь P1, выдаёшь, **ждёшь подтверждения/правок**;
  затем P2, выдаёшь, **ждёшь подтверждения/правок**; после этого выполняешь P3–P8
  пакетно и формируешь отчёт. Контрольные точки на P1/P2 — потому что атрибуция и ASR
  ошибкоопасны и всё ниже от них зависит.
- `последовательный`: подтверждение после каждого протокола.
- `пакетный`: все протоколы и отчёт в один проход (для быстрой черновой выжимки;
  P1/P2-ошибки не будут перехвачены).

**Токены подтверждения пользователя:** «готово», «принято», «далее», «ок».

**Правила работы с таймкодами:**
- Формат: `[ММ:СС]` или `[ЧЧ:ММ:СС]`.
- Невалидны СЕКУНДЫ ≥ 60, не минуты. `[75:64]` → 75 минут валидно, 64 секунды нет;
  вероятно `[76:04]` или глитч — пометить, не выкидывать всю навигацию.
- Если таймкодов нет вообще → навигация по `[строка N]` (вход должен быть пронумерован
  при загрузке). Это отдельный случай от «один битый таймкод».

## Протокол 0 (опциональный): Конфиденциальность

**Включается параметром:** `конфиденциальность: да`. Для выдуманной компании — **выключен**.

**Цель:** не вынести наружу PII и чувствительные данные реального заказчика.

> Для реальных аудитов конкретные обязанности зависят от категории ИС (КИИ/ИСПДн),
> класса защищённости и договора. Этот протокол — базовая санитизация, а НЕ замена
> сверке с внутренними требованиями. Маппинг на ФСТЭК/ГОСТ Р 57580 делается отдельно.

### Правила псевдонимизации:
| Сущность | Действие |
|----------|----------|
| Название организации | → «Заказчик» / `ORG-1` |
| ФИО | → роль или `A1`/`A2` (как в P1) |
| Внутренние хосты/IP/домены | → обобщить или замаскировать |
| Security-findings, детали инфраструктуры | не дублировать в сводку без необходимости |
| Реквизиты, контакты | удалить |

⏸️ **КОНТРОЛЬНАЯ ТОЧКА** (если включён)

## Протокол 1: Идентификация участников

**Цель:** определить количество и роли собеседников.

### Задачи:
1. Подсчитать уникальных спикеров.
2. Определить роли.
3. Присвоить ID **только при высокой уверенности** (см. Правило 2). Неуверенные — `A?`.
4. Выявить упомянутых, но отсутствующих.

### Идентификация без маркеров спикеров:
| Признак | Пример | Что определяет |
|---------|--------|----------------|
| Прямое обращение | «Андрей, скажи пожалуйста» | Имя собеседника |
| Представление | «Я — Дмитрий, РП по AppSec» | Имя + роль |
| Ролевой контекст | «Как техлид скажу...» | Роль |
| Контекст ответа | После вопроса к Андрею — ответ от Андрея | Атрибуция (если однозначна) |

### Формат вывода:
```markdown
## Протокол 1: Участники

### Идентифицировано спикеров: N (из них с высокой уверенностью: M)

| ID | Имя/Обозначение | Роль | Организация | Признаки идентификации | Уверенность |
|----|-----------------|------|-------------|------------------------|-------------|
| A1 | Владимир | Техлид backend | Заказчик | Представился [04:35] | высокая |
| A? | (неизвестно) | Возможно DevOps | ? | Реплики [12:10–14:00], без представления | низкая |

### Упомянутые, но не присутствующие:
| Имя/Роль | Контекст | Таймкод |
|----------|----------|---------|

### Неопределённости:
- [реплики, которые не удалось уверенно атрибутировать — перечислить с таймкодами]
```

**Примечание:** ID (`A1`, `A2`...) используются ниже только если присвоены при высокой
уверенности. Неуверенные реплики не получают стабильный ID.

### Критерии успеха:
- [ ] Определено количество участников (и сколько из них уверенно)
- [ ] ID присвоены только при высокой уверенности
- [ ] Указаны роли и организации
- [ ] Неатрибутированные реплики перечислены явно

⏸️ **КОНТРОЛЬНАЯ ТОЧКА**

## Протокол 2: Остаточные ошибки ASR и терминология

**Цель:** найти остаточные ошибки распознавания, искажающие смысл.

> Текст уже прошёл Whisper + Qwen. Ожидание: ошибок немного, фокус — на технических
> терминах и смысловых искажениях, переживших коррекцию. Идёт ПЕРЕД очисткой (сначала смысл).

### Типы ошибок (по приоритету):
| Тип | Описание | Приоритет | Пример |
|-----|----------|-----------|--------|
| **ASR-термины** | Технические термины искажены | Критичный | «киклог» → Keycloak |
| **ASR-смысловые** | Слова искажены до потери смысла | Критичный | «ледоносный» → вредоносный |
| **Терминологические** | Неверные аббревиатуры | Критичный | «САСТ» → SAST |
| **Орфографические** | Опечатки | Средний | «шканирование» → сканирование |
| **Лексические** | Неточное словоупотребление | Низкий | «озвучить» → назвать |

### Context-gated автозамена (важно — не lossy):
- Автозамена применяется **только при однозначном контексте**. Омонимы и легитимные
  термины (`SaaS`, `Volki/Valkey`, `trust/транш`) НЕ заменяются глобально.
- Пример: `SaaS → SAST` **только** рядом с контекстом security-testing; иначе `SaaS`
  остаётся `SaaS`.
- Все неоднозначные случаи идут в отдельную таблицу на ручное решение, НЕ в словарь автозамен.

### Формат вывода:
```markdown
## Протокол 2: Остаточные ошибки ASR и терминология

### Статистика (оценочно):
- Всего ошибок: ~N
- Критичных (термины, смысловые): ~X
- Средних (орфография): ~Y
- Низких (лексика): ~Z

### Словарь автозамен (безопасных, context-gated):
| Найти | Заменить на | Условие контекста | Частота | Приоритет |
|-------|-------------|-------------------|---------|-----------|
| киклог | Keycloak | — (однозначно) | ~2 | Критичный |
| даст | DAST | рядом security/scanning | ~2 | Критичный |
| ... | ... | ... | ... | ... |

### Таблица ошибок (детально):
| № | Таймкод/строка | Исходное | Исправление | Тип | Уверенность |
|---|----------------|----------|-------------|-----|-------------|
| 1 | [мм:сс] | «киклог» | Keycloak | ASR-термин | высокая |

### Неоднозначные случаи (НЕ автозаменять — решение вручную):
| Таймкод/строка | Слово | Варианты | Контекст |
|----------------|-------|----------|----------|
| [мм:сс] | «траст» | trust / транш | нужен контекст |
| [мм:сс] | «саас» | SaaS / SAST | нужен контекст |
```

### Критерии успеха:
- [ ] Остаточные ASR-искажения терминов найдены
- [ ] Автозамены context-gated, омонимы не тронуты
- [ ] Неоднозначные случаи вынесены отдельно
- [ ] Счётчики помечены как оценочные

⏸️ **КОНТРОЛЬНАЯ ТОЧКА** (последняя в гибридном режиме; далее — пакетно)

## Протокол 3: Очистка текста

**Цель:** выявить элементы устной речи для очистки. Счётчики — оценочные.

| Категория | Примеры | Действие |
|-----------|---------|----------|
| Слова-паразиты | «ну», «вот», «типа», «как бы» | Удалить (строгая) / пометить (мягкая) |
| Повторы | «да-да-да», повтор фраз | Сократить |
| Незаконченные фразы | Оборванные предложения | Пометить, вероятный смысл — `(вывод)` |
| Междометия | «э-э», «м-м», «ага» | Удалить |
| Слова-связки | «скажем так», «грубо говоря» | По контексту |

```markdown
## Протокол 3: Очистка текста

### Статистика (оценочно):
- Слов-паразитов: ~X | Повторов: ~Y | Незаконченных фраз: ~Z | Междометий: ~W

### Топ слов-паразитов:
| Слово | Кол-во (оценка) | Рекомендация |
|-------|-----------------|--------------|
| «вот» | ~85 | Удалить |

### Незаконченные фразы (если есть):
| Таймкод/строка | Фрагмент | Вероятный смысл (вывод) |
|----------------|----------|-------------------------|
```

### Критерии успеха:
- [ ] Категории подсчитаны (оценочно)
- [ ] Топ паразитов составлен
- [ ] Незаконченные фразы помечены, домыслы отделены

## Протокол 5: Software и архитектура (ключевой для инфра-транскриптов)

потоки данных. **Строго по тексту** — версии и связи не выдумывать (Правила 3, 7).

## Протокол 7: Обещания, решения, задачи и gaps

**Цель:** извлечь, **кто кому что обещал**, какие решения приняты, какие задачи и где
дыры. Это ядро отчёта. Без дублирования (элемент — в одном месте, остальное — ссылки).

```markdown
## Протокол 7: Обещания, решения, задачи и gaps

### Статистика:
- Обещаний: P | Решений: X | Задач: Y (с дедлайнами: Z) | Отложено: W | Gaps: N

### Обещания (кто → кому → что):
| № | Кто (от) | Кому | Что обещано | Тип | Таймкод | Уверенность |
|---|----------|------|-------------|-----|---------|-------------|
| 1 | A1 | A2 | Прислать схему архитектуры до пятницы | явное | [40:10] | высокая |
| 2 | A3 | всем | «Посмотрим, что можно сделать» по доступам | подразумеваемое | [55:30] | средняя |

> Тип: «явное» (прямое обязательство) / «подразумеваемое» (мягкая формулировка).
> Атрибуция «от/кому» при неуверенности — помечается `[атрибуция неточная]`.

### Принятые решения:
| № | Решение | Кто | Таймкод |
|---|---------|-----|---------|

### Задачи (Action Items):
| № | Задача | Ответственный | Дедлайн | Приоритет | Закрывает gap | Связь с обещанием |
|---|--------|---------------|---------|-----------|---------------|-------------------|
| 1 | Предоставить схему архитектуры | A1 | пятница | Высокий | Gap #1 | Обещание #1 |

### Выявленные gaps (проблемы):
| № | Gap | Влияние | Задача для закрытия | Ответственный |
|---|-----|---------|---------------------|---------------|
| 1 | Архитектура не задокументирована | Риск для аудита | Задача #1 | A1 |
| 2 | SAST не в pipeline | Нет автопроверки | — (нет задачи) | — |

### Отложенные вопросы:
| № | Вопрос | Причина | Когда вернуться |
|---|--------|---------|-----------------|

### Упомянутые даты:
| Дата/Срок | Контекст | Таймкод |
|-----------|----------|---------|
```

### Критерии успеха:
- [ ] Обещания извлечены в формате кто → кому → что
- [ ] Решения и задачи извлечены, задачи связаны с обещаниями/gaps
- [ ] Видно, какие gaps НЕ закрыты задачами
- [ ] Неуверенная атрибуция помечена

## Протокол 9 (опциональный): Самооценка зрелости по заявлениям

**Включается параметром:** `оценка_зрелости: да`.

> **Важно про методологию.** Это НЕ оценка зрелости процесса. Maturity (CMMI-подобное)
> определяется по артефактам и во времени, а не по тому, что люди рассказали на одной
> встрече (рассказ может быть аспирационным или защитным). Здесь фиксируется
> **самооценка по заявлениям, не верифицированная**. Допустимо «недостаточно данных».
> Выдавать диапазон, а не точку. Для реальной оценки — отдельный аудит артефактов.

### Шкала (1–5, как ориентир заявленного уровня):
| Уровень | Описание |
|---------|----------|
| 1 | Отсутствует / Хаотично |
| 2 | Начальный / Реактивный |
| 3 | Определённый / Документированный |
| 4 | Управляемый / Измеряемый |
| 5 | Оптимизируемый |

```markdown
## Протокол 9: Самооценка зрелости (по заявлениям, не верифицировано)

### Заявленный диапазон: X–Y / 5

| Процесс/Область | Заявл. уровень | Основание (цитата) | Таймкод | Достоверность |
|-----------------|----------------|--------------------|---------|---------------|
| SAST | 1–2 | «Не встроен в pipeline» | [28:15] | со слов |
| Unit-тестирование | 3–4 | «Обязательны, блокируют релиз» | [16:13] | со слов |
| Управление доступами | недостаточно данных | — | — | — |

### Рекомендации (как гипотезы, требуют верификации):
| Область | Заявл. | Целевой | Что проверить/сделать |
|---------|--------|---------|-----------------------|
```

### Критерии успеха:
- [ ] Оценки даны как заявленные, не как факт
- [ ] Где данных мало — «недостаточно данных»
- [ ] Рекомендации помечены как требующие верификации
